## 2. Постановка задачи и контекст

### Предметная область и задача

Предметная область проекта - поиск информации по локальной базе знаний. Такая задача возникает, когда у пользователя есть набор заметок, документации, учебных материалов или внутренних текстовых файлов, и нужно быстро находить релевантные фрагменты по естественно-языковому запросу.

Потенциальный пользователь сервиса - студент, разработчик или автор технических заметок, который хочет искать информацию по своей базе Markdown-документов через API. Например, пользователь может задать вопрос: «Как сделать Dockerfile для FastAPI-сервиса?», а система должна найти заметки, связанные с Docker и FastAPI.

По типу задачи проект относится к NLP/retrieval-задачам. Дополнительно используется бинарная классификация релевантности пары `query + chunk`.

### Формулировка задачи в терминах ML/ИИ

Входные данные:

* пользовательский текстовый запрос `query`;
* набор текстовых заметок в формате Markdown;
* подготовленные текстовые чанки документов;
* пары `query + chunk` с разметкой релевантности.

Выход модели/сервиса:

* список найденных чанков;
* идентификатор исходного документа;
* score поиска;
* score релевантности;
* флаг `answerable`, показывающий, достаточно ли найденного контекста;
* текстовый ответ на основе наиболее релевантного фрагмента.

Целевая переменная для классификатора релевантности - бинарная метка:

* `1` - чанк релевантен запросу;
* `0` - чанк не релевантен запросу.

Основные ограничения:

* сервис должен быстро отвечать на запросы;
* решение должно быть воспроизводимым через Docker;
* модель должна быть достаточно простой и интерпретируемой;
* проект не должен требовать внешних API-ключей или закрытых данных;
* все демонстрационные данные должны храниться в репозитории.

### Целевые метрики качества

Для оценки retrieval-части используются:

* `Precision@1` - показывает, как часто первый найденный результат является релевантным;
* `Precision@3` - показывает долю релевантных результатов среди первых трёх найденных;
* `Recall@5` - показывает, была ли релевантная информация найдена среди первых пяти результатов;
* `MRR` - оценивает позицию первого релевантного результата в выдаче.

Эти метрики выбраны, потому что для поискового сервиса важна не только сама классификация, но и порядок найденных документов. В практическом сценарии особенно важен первый результат, так как именно он используется для формирования ответа.

Для классификатора релевантности используются:

* `Accuracy`;
* `Precision`;
* `Recall`;
* `F1-score`;
* `Macro F1`.

Эти метрики позволяют оценить качество бинарной классификации пары `query + chunk`, а `Macro F1` дополнительно учитывает баланс между классами.

## 3. Данные

### Источник данных

В проекте используется демонстрационная локальная база заметок в формате Markdown. Данные являются синтетическими/учебными и находятся в папке `data/notes/`.

В базе представлены короткие технические заметки по темам:

* FastAPI;
* Docker;
* RAG;
* ML-метрики;
* EDA;
* логирование;
* TTS-пайплайны;
* Kotlin ClassLoader.

Для обучения и оценки релевантности используется файл `data/qrels.csv`, в котором заданы пары пользовательских запросов и релевантных или нерелевантных документов/чанков.

### Структура данных

Основные файлы данных:

* `data/notes/*.md` - Markdown-документы с текстовыми заметками;
* `data/qrels.csv` - разметка релевантности;
* `artifacts/` - сохранённые модели и индексы;
* `reports/eda.json` - результаты разведочного анализа данных;
* `reports/retrieval_metrics.json` - метрики поиска;
* `reports/classification_report.json` - отчёт по классификатору релевантности.

Структура `qrels.csv` содержит пары вида:

* пользовательский запрос;
* идентификатор документа или чанка;
* бинарная метка релевантности.

Данные являются текстовыми. Основная предобработка связана с чтением Markdown-файлов, разбиением документов на чанки и формированием пар `query + chunk`.

### Предобработка и EDA

Предобработка выполняется скриптом:

```bash
python -m src.data.prepare_dataset
```

На этом этапе:

* загружаются Markdown-файлы из `data/notes/`;
* документы разбиваются на текстовые чанки;
* каждому чанку присваивается идентификатор;
* формируются подготовленные данные для поиска, обучения и оценки.

Разведочный анализ данных выполняется командой:

```bash
python -m src.data.eda
```

По результатам EDA текущий демонстрационный корпус содержит:

* количество документов: 8;
* количество чанков: 8;
* средняя длина чанка: 325.75 символов;
* минимальная длина чанка: 270 символов;
* максимальная длина чанка: 375 символов;
* количество размеченных пар `query + chunk`: 26;
* положительных пар: 14;
* отрицательных пар: 12;
* доля положительных примеров: 0.538.

EDA показывает, что корпус является небольшим, но для демонстрации подходит. Классы релевантности распределены относительно равномерно: положительных примеров немного больше, чем отрицательных, но сильного дисбаланса нет.

Основное ограничение данных - малый объём корпуса и разметки. Из-за этого метрики классификатора могут быть нестабильными, а результаты следует рассматривать как демонстрацию работоспособности пайплайна, а не как полноценный продукт.

## 4. Модели и подходы

### Базовые модели

В качестве baseline-подхода используется TF-IDF retrieval.

Документы преобразуются в TF-IDF-векторы, после чего для пользовательского запроса вычисляется близость с чанками документов. Наиболее похожие чанки возвращаются как результаты поиска.

Преимущества baseline-подхода:

* простая реализация;
* высокая скорость работы;
* интерпретируемость;
* отсутствие необходимости в тяжёлых нейросетевых моделях;
* возможность запуска в Docker без GPU и внешних API.

По результатам экспериментов TF-IDF показал высокое качество поиска на демонстрационном корпусе:

* `Precision@1`: 0.923;
* `Precision@3`: 0.333;
* `Recall@5`: 0.962;
* `MRR`: 0.949.

Высокие `Precision@1` и `MRR` показывают, что в большинстве случаев релевантный документ оказывается на первой позиции или близко к началу выдачи.

### Улучшенные модели и эксперименты

Поверх baseline-поиска был добавлен классификатор релевантности пары `query + chunk`. Он решает бинарную задачу: определить, является ли найденный чанк релевантным пользовательскому запросу.

Для классификатора используются признаки:

* cosine similarity между TF-IDF-векторами запроса и чанка;
* пересечение токенов запроса и чанка;
* длина запроса;
* длина чанка;
* количество токенов в запросе;
* количество токенов в чанке.

В качестве модели используется `LogisticRegression`.

Результаты классификатора на тестовой части:

* `Accuracy`: 0.429;
* `Macro F1`: 0.417;
* `F1` для класса `0`: 0.333;
* `F1` для класса `1`: 0.500.

Эти результаты показывают, что на текущем маленьком датасете классификатор релевантности работает нестабильно. Поэтому в финальном пайплайне основной вес отдаётся retrieval-score, а классификатор используется как дополнительный экспериментальный сигнал для reranking и определения `answerable`.

### Нейросетевые модели

В базовой версии проекта нейросетевые модели не используются, чтобы сохранить простоту запуска и воспроизводимость. Проект не требует GPU и внешних API-ключей.

В дальнейшем возможно подключение embedding-модели, например multilingual SentenceTransformer. Это позволит улучшить качество поиска для случаев, когда запрос и документ используют разные формулировки, но имеют близкий смысл.

## 5. Экспериментальный протокол и результаты

### Экспериментальный протокол

Эксперименты проводились на демонстрационной базе заметок и файле разметки `data/qrels.csv`.

Общий пайплайн эксперимента:

1. Загрузка Markdown-документов.
2. Разбиение документов на чанки.
3. Построение TF-IDF-индекса.
4. Обучение классификатора релевантности на парах `query + chunk`.
5. Оценка retrieval-метрик.
6. Оценка классификатора релевантности.
7. Сохранение артефактов модели и отчётов.

Для retrieval-задачи качество оценивалось по тому, попадает ли релевантный документ в top-K результатов. Использовались метрики `Precision@1`, `Precision@3`, `Recall@5` и `MRR`.

Для классификатора релевантности использовались стандартные метрики бинарной классификации: `Accuracy`, `Precision`, `Recall`, `F1-score` и `Macro F1`.

Так как набор данных небольшой, результаты экспериментов следует интерпретировать осторожно. Основная цель экспериментов - показать воспроизводимый процесс обучения, оценки и выбора финального подхода.

### Сравнение моделей по метрикам

| Модель / конфигурация                   | Описание                                                                                                                     |                                     Ключевые метрики | Комментарий                                            |
|-----------------------------------------|------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------:|--------------------------------------------------------|
| TF-IDF retrieval                        | Поиск по TF-IDF-векторам и cosine similarity                                                                                 |   Precision@1 = 0.923, Recall@5 = 0.962, MRR = 0.949 | Хорошо подходит для текущего демонстрационного корпуса |
| LogisticRegression relevance classifier | Бинарная классификация пары `query + chunk` по TF-IDF и простым текстовым признакам                                          |                   Accuracy = 0.429, Macro F1 = 0.417 | На маленьком датасете работает нестабильно             |
| TF-IDF retrieval + relevance score      | Комбинированный подход: retrieval-score как основной сигнал, классификатор как дополнительный reranking/answerability-сигнал | Используются retrieval-метрики и score релевантности | Выбран как финальный подход                            |

### Выбор финальной модели

В качестве финального подхода выбран TF-IDF retrieval с дополнительной оценкой релевантности.

Причины выбора:

* TF-IDF retrieval показал хорошие retrieval-метрики на демонстрационном корпусе;
* подход быстро работает и легко воспроизводится;
* он не требует GPU, внешних API или скачивания больших моделей;
* результаты поиска интерпретируемы;
* классификатор релевантности можно использовать как дополнительный сигнал, но не как единственный критерий принятия решения.

Основное допущение проекта заключается в выборе между простотой и качеством семантического поиска. TF-IDF хорошо работает на небольшом корпусе с близкими формулировками запросов и документов, но хуже обрабатывает сложные семантические совпадения. Для улучшения качества в дальнейшем можно подключить embedding-модель и reranker.

## 6. Архитектура решения и сервис

### Архитектура пайплайна

Архитектура проекта состоит из нескольких этапов:

> Markdown notes -> Data preparation / chunking -> EDA -> TF-IDF index -> Relevance classifier ->  FastAPI service -> /health и /predict

Основные компоненты проекта:

* `src/data/prepare_dataset.py` - подготовка данных;
* `src/data/eda.py` - разведочный анализ данных;
* `src/models/retrieval.py` - построение и использование поискового индекса;
* `src/models/features.py` - выделение признаков для пары `query + chunk`;
* `src/models/train.py` - обучение модели релевантности;
* `src/models/evaluate.py` - расчёт метрик;
* `src/service/app.py` - FastAPI-приложение;
* `src/service/schemas.py` - Pydantic-схемы запросов и ответов.

### API и endpoints

В сервисе реализованы два основных endpoint’а.

#### `/health`

Метод:

```http
GET /health
```

Назначение endpoint’а - проверить, что сервис запущен и артефакты модели загружены.

Пример ответа:

```json
{
  "status": "ok",
  "artifacts_loaded": true,
  "retrieval_mode": "tfidf"
}
```

#### `/predict`

Метод:

```http
POST /predict
```

Endpoint принимает пользовательский запрос и количество результатов `top_k`.

Пример запроса:

```json
{
  "query": "Как сделать Dockerfile для FastAPI сервиса?",
  "top_k": 3
}
```

Пример ответа:

```json
{
  "query": "Как сделать Dockerfile для FastAPI сервиса?",
  "answerable": true,
  "answerable_score": 0.42,
  "answer": "Наиболее релевантный фрагмент найден в заметке `docker.md`...",
  "chunks": [
    {
      "chunk_id": "docker.md::chunk_0",
      "doc_id": "docker.md",
      "text": "...",
      "retrieval_score": 0.13,
      "relevance_score": 0.44
    }
  ],
  "retrieval_mode": "tfidf"
}
```

* большие пользовательские данные.

## 8. Ограничения и дальнейшая работа

Текущая версия проекта является учебным прототипом и имеет ряд ограничений.

Основные ограничения:

* корпус содержит только 8 демонстрационных документов;
* каждый документ представлен одним чанком;
* разметка включает только 26 пар `query + chunk`;
* классификатор релевантности показывает невысокое качество на тестовой выборке;
* TF-IDF хуже работает с синонимами и сложными семантическими переформулировками;
* генерация ответа реализована в extractive-формате на основе найденного фрагмента;
* отсутствует веб-интерфейс;
* отсутствует авторизация;
* нет загрузки пользовательских документов через API;
* нет постоянного внешнего хранилища индекса.

Если бы было больше времени, можно было бы улучшить проект следующим образом:

* расширить корпус до 50–100 документов;
* увеличить количество размеченных пар `query + chunk`;
* добавить более реалистичное разбиение длинных документов на несколько чанков;
* подключить embedding-модель, например multilingual SentenceTransformer;
* добавить reranker для более точной сортировки результатов;
* реализовать генерацию ответа через локальную или внешнюю LLM;
* добавить endpoint для загрузки новых документов;
* добавить инкрементальное обновление индекса;
* сохранить индекс в FAISS, ChromaDB или SQLite;
* добавить авторизацию пользователей;
* добавить более подробное логирование запросов;
* добавить OpenAPI-примеры для основных сценариев.

## 9. Сценарий демонстрации на защите

На защите планируется показать полный сценарий работы проекта: от структуры данных до получения ответа через API.

### Что запускается

Основной запуск выполняется через Docker Compose:

```bash
docker compose up --build
```

Во время сборки и запуска выполняются основные этапы проекта:

1. установка зависимостей;
2. подготовка данных;
3. EDA;
4. обучение модели;
5. оценка качества;
6. запуск тестов;
7. запуск FastAPI-сервиса.

После запуска сервис доступен по адресу:

```text
http://localhost:8000
```

Проверка состояния сервиса:

```bash
curl http://localhost:8000/health
```

### Ключевые сценарии демонстрации

Первый сценарий - запрос по теме Docker и FastAPI:

```bat
curl -X POST http://localhost:8000/predict -H "Content-Type: application/json" -d "{\"query\":\"Как сделать Dockerfile для FastAPI сервиса?\",\"top_k\":3}"
```

Ожидаемый результат: сервис находит заметки `docker.md` и `fastapi.md`, возвращает найденные чанки, score поиска, score релевантности и ответ на основе найденного контекста.

Второй сценарий - запрос по теме RAG:

```bat
curl -X POST http://localhost:8000/predict -H "Content-Type: application/json" -d "{\"query\":\"Что такое RAG и зачем нужен retrieval?\",\"top_k\":3}"
```

Ожидаемый результат: сервис находит заметку `rag.md` и возвращает контекст, связанный с retrieval-augmented generation.

### На что обратить внимание преподавателю

Во время демонстрации стоит обратить внимание на следующие аспекты:

* проект запускается одной командой через Docker;
* endpoint `/health` показывает, что сервис работает и артефакты загружены;
* endpoint `/predict` использует реальные ML-артефакты, а не заглушку;
* сервис возвращает не только ответ, но и найденные источники;
* есть EDA и сохранённые метрики;
* реализован baseline-поиск на TF-IDF;
* обучен классификатор релевантности;
* проект имеет разделение на данные, модели, сервис, конфиги, отчёты и тесты;
* ограничения проекта честно описаны и связаны прежде всего с малым объёмом демонстрационных данных.
